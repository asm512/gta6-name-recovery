2How it works

2.1What a hash is, and why the names are missing

GTA VI, like Rockstar's earlier games, runs on the RAGE engine. Much of its configuration lives in binary metadata files. Their content is organised into structs (groups of values, such as a vehicle's handling data), fields in each struct (such as its mass) and enums (fixed lists of options, whose entries are enum values).

The game does not need the human-readable names, so it stores only a hash of each one: a fixed-size number computed from the text. RAGE uses a 32-bit function called joaat (Bob Jenkins' "one-at-a-time" hash). Computing a hash from a name is instant. Going the other way is not possible, because the number does not contain the text. The only way back is to guess a name, hash it, and see whether the number matches. The lookup at the top of this page does exactly that for whatever you type.

Struct, field and enum-value names are hashed exactly as written, so case matters: fMass and fmass give different numbers. Values stored inside the data, such as model names, are hashed in lower case.

2.2Why a match is not proof

A 32-bit hash has about 4.3 billion possible values, but there are far more possible names than that. So every hash is shared by a great many texts, almost all of them nonsense. These three all hash to 0x23762435:

fMass                  the real name
fJointCrowdFreeze
fAimedPersonInteriors

The last two were found in under a second by combining words from other names. They look plausible, which is the problem: a match proves only that the text hashes to the right number, not that it is the right name. Every step below has to deal with this.

2.3The list of names to find

The game's executable holds a table of every struct and enum its metadata parser can read. For each field the table gives the name's hash, the type, the position in the struct, the default value and, where the field holds another struct or an enum, which one. The names themselves were removed when the game was built; the slots that would hold them are empty.

That table, plus the structs that only the metadata files in the game's archives refer to, is the list of names to find: – structs with – distinct field names, and – enums with – distinct value names. The files also show which names are in actual use (Figure 3). Enum values that carry a plain number instead of a hash have no name to recover and are not counted.

2.4Names that exist as text

Rockstar kept many names from game to game, and the community has published lists of names recovered from GTA V, Red Dead Redemption 2 and other RAGE games. Every name in those lists is hashed and kept if the hash is one the game uses. This found – names, most of them from the dictionary in alexguirre/rage-parser-dumps. Examples: fMass, fInitialDragCoeff, CScenarioInfo.

A few names are also written out in the game's own files, in text that the game ships next to the hashed data. Every file of the game was searched for text that hashes to a missing name; another – names came from there, such as OverrideTimeToWaitForPassengers.

Names found this way are reliable, because the text was written by someone and not produced by a search. The largest lists are big enough to hit a few hashes by coincidence, so from loose sources only names built from words that other parser names use are kept.

2.5Searching, with chance measured

The rest have to be guessed. Known names are split into words (fInitialDragCoeff becomes f, Initial, Drag, Coeff), and a small program written in Rust recombines them at more than a billion candidates per second. It does not try them in arbitrary order: for each kind of name it learns which words tend to come first, in the middle and last (the name of a float field often starts with f, a bool with Is or Use) and tries the most probable combinations first.

Two narrower searches use what is known about one place. A struct's missing field names are tried against the words of its known fields. An enum's missing values are tried as the prefix its known values share (PCF_, VEH_EXT_) followed by words.

Because these searches try so many texts, some matches are coincidences. To measure how many, every search also runs against decoys: random hashes that belong to no name. A match against a decoy is chance by definition, so the decoy hits show how many of the real matches are probably chance too. Only the region of a search where decoys almost never match is accepted automatically. These names are marked cracked: – so far.

2.6A language model judges the candidates

Further out, a search returns several matching texts per hash, like the three for 0x23762435 above, and most are chance. Picking the right one needs context. For each hash a language model (Claude Opus 5.5 and Claude Fable 5.2) reads the candidates together with what the tables say about it: the type, the struct it belongs to, a sample or default value, the type it refers to, and the known names of its sibling fields. A float holding 1,630 in a struct of vehicle handling values suggests fMass, not fJointCrowdFreeze. The model accepts a name only where it fits that place, and is told that a wrong name is worse than a missing one. These names are marked judged: – so far.

The judging is tested the same way as the search: known names are hidden, sent through the whole process mixed with unknown ones, and the answers are checked against the truth.

2.7Limits

Reliability differs by method. Names found as text are reliable. Cracked names carry a measured chance rate of a few percent, judged names about 1 to 2%. The table in section 3 shows the method of every name.

100% is not reachable this way. A long or unusual name cannot be pinned down from a 32-bit hash: many texts fit, and nothing says which one is right. What is left is mostly names with little context, such as structs whose fields are all unknown, and names made of words that no known name uses.

Not everything is read. Every metadata file has one section (LSNS) that this project does not decode.
