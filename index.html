2How it works

2.1What a hash is, and why the names are missing

GTA VI, like Rockstar's earlier games, runs on the RAGE engine. Much of its configuration lives in binary metadata files (they start with the bytes PSIN). Each file first describes its own layout: the structs it contains (groups of values, such as a vehicle's handling data), the fields in each struct (such as its mass), and enums (fixed lists of options, whose entries are enum values).

The game does not need the human-readable names, so it stores only a hash of each name: a fixed-size number computed from the text. RAGE uses a 32-bit function called joaat (Bob Jenkins' "one-at-a-time" hash). Computing a hash from a name is instant. Going the other way is not possible: the number does not contain the text. The only way back is to guess a name, hash it, and see whether the number matches. The lookup at the top of this page does exactly that for whatever you type.

Struct, field and enum-value names are hashed exactly as written, so case matters: fMass and fmass give different numbers. (Values stored inside the data, such as model names, are hashed in lower case.) At the start of this work, names were lower-cased before hashing. That matched almost nothing: 167 names. Hashing them as written raised the game's own strings alone to 1,191.

2.2Why many texts share one hash

A 32-bit hash has about 4.3 billion possible values, but there are far more possible names than that. So every hash is shared by a great many texts, almost all of them nonsense. For example, these three names all hash to 0x23762435:

fMass                  the real name
fJointCrowdFreeze
fAimedPersonInteriors

The last two were found in under a second by combining words that occur in other recovered names. They look plausible, which is the problem: a match proves only that the text hashes to the right number, not that it is the right name. Every technique below has to deal with this.

2.3Names from earlier games

Rockstar kept many names from game to game, and the community has published lists of names recovered from GTA V and Red Dead Redemption 2. Hashing every name in those lists and looking each one up is called a dictionary attack. The list in alexguirre/rage-parser-dumps matched about 6,980 names on its own; CodeWalker and a few other sources added under 200 more, for 7,418 in total. Examples: fMass, fInitialDragCoeff, fBrakeForce, fSteeringLock.

These names are reliable. A name taken from a list is a short, specific piece of text; the chance that one of them hits the right hash by coincidence is about 1 in 200,000.

2.4Recombining known words, and measuring chance

Known names are split into words (fInitialDragCoeff becomes f, Initial, Drag, Coeff) and the words are recombined: two words together, a known name plus one word, Min/Max twins of a known name, and type prefixes such as f for floating-point numbers, checked against the field's real type. Searches can also be run per struct, using the words of the fields next to the missing one. This step brought the total to 9,401. Examples: BlendInDurationMax, AngleMinDebug.

Because these searches try many texts, some matches will be coincidences. To measure how many, every search is also run against decoys: random hashes that belong to no real name. Any match against a decoy is by definition chance, so the decoy hit rate tells how many of the real matches are probably chance too. Searches whose matches are mostly chance are thrown away. Names kept from this step carry a measured chance rate of a few percent.

2.5Probability-ranked cracking

A small program written in Rust tries more than a billion candidate names per second. It does not try them in arbitrary order: it estimates how likely each word is in each position for each kind of field (for instance, the name of a float field usually starts with f) and tries the most probable combinations first. Only matches in the most probable region are accepted automatically. fTorqueCurve and the struct name ChassisHandlingData were found this way.

2.6A language model judges the candidates

Further out, brute force returns several matching texts per hash, like the three for 0x23762435 above. Picking the right one needs context, so language-model agents read each hash's candidates together with what is known about it: the value type, the struct it belongs to, the names of its sibling fields and a sample value from the data (a car with a mass of 1,630 suggests fMass, not fJointCrowdFreeze). They accept only names that make sense in that place. The agents also wrote topic vocabularies and per-struct vocabularies to feed back into the cracker.

Together with the cracker, this added about 2,200 names over several rounds, with shrinking returns: roughly 1,500 in the first round, then 400, then a few hundred. Of the current names, – are marked as judged; the others from these rounds were accepted automatically and are marked as cracked.

2.7Limits

Scope. The figure covers the metadata in three archives (common.rpf, script.rpf, data.rpf), not the whole game.

Reliability differs by method. Names found in lists or in the game's own text are reliable (a chance collision is about 1 in 200,000 per name). Automatically built names (word combinations and cracking) carry a measured chance rate of a few percent. The error rate of model-judged names has not been measured yet; it is estimated at a few percent, and a held-out test is planned. The table in section 3 shows the method of every name.

100% is not reachable this way. A long or unusual name cannot be pinned down from a 32-bit hash: many texts fit, and nothing in the data says which one is right. The realistic ceiling without the game executable is estimated at 60 to 70%.

One section stays unreadable. One section of every file (LSNS) consists of 16-byte records with no visible structure. It cannot be read without a key or algorithm that is not in the game files.
